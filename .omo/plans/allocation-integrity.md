# allocation-integrity - Work Plan

## TL;DR (For humans)
(What you'll get / Why this approach / What it will NOT do / Effort / Risk / Decisions)
- You'll get: a persistence layer that can never accumulate duplicate allocations, a unique-index backstop, an engine that preserves your manual/locked assignments on recalculation and merges into existing rows (at most one row per identity), manual allocate/release endpoints with backend-authoritative physical-card validation, and a regression suite that locks all of it in.
- Why this approach: the root cause is verified as additive-only `writeDb` (pure upsert, zero deletes) combined with fresh ids per auto-allocate run. Fixing persistence makes the system correct regardless of id generation; the UNIQUE index makes it impossible by construction; engine lock-preservation + merge-into-existing keeps manual allocation meaningful and ensures at most one row per identity.
- What it will NOT do: rebuild the card database, change PTCG API sync, replace SQLite, redesign unrelated UI/architecture, rewrite the app, or add dependencies/abstractions (per your brief).
- Effort: ~10 implementation todos across 5 components (DB layer, engine, backend API, frontend, tests).
- Risk: migration touches the live `data/cards.db` allocations table (dedupe is destructive by design — keep-newest as duplicate representation of same logical allocation, do NOT sum quantities; preserve isLocked from kept row). Mitigated by deterministic keep-newest logic, invariant verification post-dedupe, a backfill test on a temp DB, and `npm run lint`/`test` gates before any write path changes land.
- Decisions: keep-newest dedupe per identity (F1) · locked allocations preserved on recalc (F2) · TDD in existing console.assert/tsx style, no new framework (F3) · root-cause fix = writeDb reconciliation (approved in brief) · engine merges into existing rows (at most one per identity) · all writeDb callers verified complete-state · duplicates are NOT additive (keep newest row, do not sum).

## Scope
IN:
- `server/database/index.ts` + `server/database/schema.ts`: allocation dedupe migration (keep-newest per identity as duplicate representation of same logical allocation — do NOT sum quantities; preserve isLocked from kept row; verify physical/requirement invariants post-dedupe), unique index, writeDb reconciliation (delete rows whose id is absent from incoming state, guarded by `data.allocations !== undefined`), UNIQUE table constraint for fresh DBs. All writeDb callers verified complete-state (server.ts, cardSync.ts, init.ts, tests).
- `src/services/allocationEngine.ts`: `autoAllocateDeck` preserves `isLocked` rows for the target deck; merges into existing rows when identity matches (at most one row per identity); locked rows count against item availability and requirement satisfaction; unlocked rows created only when no identity match exists.
- `server.ts`: shared `validateAllocationInvariants` helper; new `POST /api/allocations/allocate` and `POST /api/allocations/release` endpoints; enforce invariant on collection qty changes, move, allocate, release; add `allocationId` to `GET /api/collection` allocatedDetails.
- `src/services/api.ts`: `allocateToDeck`, `releaseAllocation` client functions.
- `src/components/Allocations/AllocationsDashboard.tsx`: manual allocate form + release control (minimal, matching existing card style).
- New test files `tests/allocationDuplicateRegression.test.ts`, `tests/allocationLock.test.ts`, `tests/allocationInvariant.test.ts`; register all in `package.json` `test` chain.

OUT (Must-NOT-Have):
- No card-database rebuild, no PTCG API sync changes (`server/cardSync.ts` behavior unchanged), no SQLite replacement, no unrelated UI/architecture redesign, no app rewrite, no new dependencies, no new test framework, no abstractions beyond one shared validation helper.
- No changes to `calculateCardOwnershipForDeck` semantics (it consumes whatever allocations exist; with duplicates gone it reports correct numbers — leave its logic intact).
- No auto-allocate triggers added anywhere (the codebase deliberately only auto-allocates on the explicit endpoint / deck delete re-balance — preserve that contract).

## Verification strategy
- TDD: each implementation todo is preceded by its failing test todo; tests are plain `tsx` + `console.assert` scripts (existing style) chained in `npm test`.
- Gates: `npm test` (existing 5-file chain + 3 new files) and `npm run lint` (`tsc --noEmit`) and `npm run build` (vite + esbuild) must pass at the end of each wave.
- Migration correctness proven on a temp DB file (not the live `data/cards.db`): seed duplicates with known ids, run the exported migration function, assert keep-newest outcome + index existence.
- Manual QA: start dev server (`npm run dev`), log in, auto-allocate twice, then inspect `GET /api/collection` / allocations for zero duplicate identities; exercise allocate/release/move in the dashboard.

## Execution strategy
Waves (dependency order — persistence first because it is the root cause, then engine, then API, then UI; tests woven in TDD order):
1. **Wave 1 - DB layer (C1):** failing duplicate-regression tests → migration function (keep-newest per identity, preserving legitimate allocation quantity) + UNIQUE constraint + writeDb reconciliation (delete rows whose id is absent from incoming state, guarded by `data.allocations !== undefined`; all writeDb callers verified complete-state).
2. **Wave 2 - Engine (C2):** failing lock tests → `autoAllocateDeck` lock preservation + merge-into-existing-rows (at most one row per identity).
3. **Wave 3 - Backend API (C3):** failing invariant tests (pure-function level) → shared validation helper + allocate/release endpoints + move/collection enforcement.
4. **Wave 4 - Frontend (C4):** api.ts client + dashboard UI (allocate form, release button).
5. **Wave 5 - Full verification:** `npm test` + `npm run lint` + `npm run build` + manual QA.

Dependency matrix: T2 depends on T1 (tests must fail first); T4 depends on T3; T6 depends on T5; T7 depends on T6; T8 depends on T7; T9 depends on T8; T10 (full verification) depends on all.

## Success criteria
- `data/cards.db` allocations contain zero duplicate (deckId, requirementId, collectionItemId) identities after any sequence of auto-allocate / manual allocate / release / move / collection edits.
- At most one allocation row per identity exists in the database at all times (enforced by engine merge-into-existing + UNIQUE constraint).
- The unique index exists on the live DB and on all fresh DBs; the migration is idempotent and preserves the canonical/newest row (duplicates are NOT additive — do not sum quantities).
- writeDb reconciliation safely deletes stale rows without affecting valid allocations (all callers verified complete-state).
- Post-migration physical/requirement invariants are verified correct on existing data.
- Locked allocations survive every "Recalculate All Allocations" run and prevent over-allocation by construction.
- Manual allocate/release work through both API and UI, always backend-validated (never trusting frontend quantities).
- `npm test` (8 files), `npm run lint`, and `npm run build` all pass.
- All four final-verification items (F1-F4) APPROVE with recorded evidence.
